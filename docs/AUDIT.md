## 1. 摘要

### 做对了什么

- **定位选得准**。同类扩展大多停留在「点一下休眠」，本项目真正解决的是
  **浏览器重启时会话恢复导致的内存雪崩**（启动抢先休眠），这是有真实痛点的差异化能力。
- **技术选型正确**。坚持使用原生 `chrome.tabs.discard()`，不做占位页替换 DOM
  —— 同类扩展的历史事故几乎都源于占位页方案。
- **尊重浏览器生命周期**。启动休眠窗口只认 `chrome.runtime.onStartup`，
  用 `chrome.storage.session` 跨 Worker 回收保存窗口边界，这是 MV3 下少见的细致处理。
- 无构建步骤、原生 ES Module，`src/` 直接可加载，贡献者上手成本极低。

### 关键问题

| 类别      | 数量 | 说明                                                     |
| --------- | ---- | -------------------------------------------------------- |
| 阻断级 P0 | 4    | 功能静默失效、文档承诺的能力不存在、发布链路不可用       |
| 重要 P1   | 8    | 数据丢失、功能实际不生效、上帝模块、重复实现、可测性缺失 |
| 改进 P2   | 15   | 死代码、竞态、校验缺口、国际化漏洞、协作护栏缺失         |
| 建议 P3   | 6    | 脚本质量、权限最小化、文档语言、品牌风险                 |

最具代表性的一条：**弹窗里的「唤醒」按钮从未触发过状态恢复**。
它直接调用 `chrome.tabs.reload()`，完全绕过了 Service Worker 的唤醒处理，
而滚动位置/表单内容恢复的握手逻辑恰恰只存在于那条被绕过的路径上。
功能一直在，测试从没覆盖，用户每次点唤醒都少一次统计、丢一次滚动位置。

## 3. 定位评估：目标与应用场景

审计前，项目**没有**一份明确的目标陈述。README 开场主打「内存告急时一键减负」，
但这恰恰是同类扩展的红海卖点；真正独特、且工程量最大的启动抢先休眠被排在
功能表第 2 行、文档深处。结果是：**产品最强的能力没有出现在价值主张里**。

整改后已在 [ARCHITECTURE.md 第 1 节](ARCHITECTURE.md#1-项目定位) 明确：

- **目标**（5 条，可验证）
- **非目标**（5 条边界：不做标签页管理器、不做假页面、不保留页面内 JS 状态、
  不跨浏览器、不引入构建步骤）
- **应用场景**（3 个具体场景）

README 也已重写为「先讲重启雪崩，再讲一键减负」的顺序。

## 4. 架构评估

### 整改前的结构

```
popup.js ─┐
options.js ─┴─ sendMessage ─▶ service-worker.js  ← 1025 行
                                    │   消息路由 / 休眠 / 批处理 /
                                    │   自动休眠 / 启动休眠 / 角标 /
                                    │   右键菜单 / favicon 代理  全部混在一起
                                    ▼
                              utils/{storage,tab-manager,whitelist,constants}
                                    ▲
                       content-script.js（自己的表单逻辑 + 无人调用的协议）
```

### 分层本身是对的

UI → 消息 → Service Worker → utils → Chrome API 的链路清晰，
`MESSAGE_TYPES` 作为契约、`DEFAULT_SETTINGS` 作为默认值的单一来源，这些都对。
问题不在分层思想，而在**执行纪律**。

### 问题

| 编号   | 问题                                                                                                                                           | 证据                                                                                 |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| ARCH-1 | **上帝模块**：`service-worker.js` 1025 行，混合 8 类职责（消息路由、单页休眠、批处理状态机、自动休眠、启动休眠、角标、右键菜单、favicon 代理） | 全文件；仅"启动休眠"一段就占 240 行                                                  |
| ARCH-2 | **导入即副作用**：所有 `chrome.*.addListener` 与 `const ready = initStartupSuspend()` 都在模块顶层执行                                         | 顶层即有 20+ 处监听注册与初始化调用                                                  |
| ARCH-3 | **重复实现**：白名单匹配 3 份、浏览器内部页面判定 3 份、表单采集 2 份；`CHROME_INTERNAL_SCHEMES` 常量定义了却无人使用                          | `whitelist.js:24`、`popup.js:368`、`service-worker.js:901`；常量在 `constants.js:64` |
| ARCH-4 | **内容脚本携带死协议**：`captureState` / `restoreState` 两个消息分支无人发送                                                                   | `content-script.js:84-113`；SW 改用 `executeScript` 内联函数                         |
| ARCH-5 | **可测性缺失**：逻辑与 Chrome API 注册耦合，只能靠手写 mock 全量加载模块来测                                                                   | 既有测试正是这么做的（349 行脚手架）                                                 |

## 9. 对项目所有者的建议

1. **把价值主张改成"重启不再雪崩"**。启动抢先休眠是唯一有护城河的能力，
   一键休眠谁都有。README 已按此重写，应用商店文案建议同步。
2. **优先做权限最小化（N1 + L1）**。这两项直接决定商店审核通过与用户信任，
   收益高于任何新功能。
3. **在确定品牌名之后再投入推广**。改名成本随用户量增长，现在是成本最低的时刻。
4. **保持零构建、零运行时依赖这条线**。它让「克隆 → 加载 `src/` → 改完刷新」
   这个循环保持在 30 秒以内，是这个项目最被低估的协作优势。
