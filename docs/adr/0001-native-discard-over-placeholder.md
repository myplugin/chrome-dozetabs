# 0001. 用原生 discard，不做占位页

- **状态**：已采纳
- **日期**：2026-03-17（回溯记录）
- **影响**：全部休眠路径、`manifest.json` 权限、用户体验与信任

## 背景

要把标签页"挂起"，Chromium 内核上有两条路：

1. **原生 `chrome.tabs.discard(tabId)`** —— 浏览器卸载页面的渲染进程，
   保留标签页本身（标题、图标、位置）。用户点击时浏览器重新加载。
2. **占位页方案** —— 扩展用 `chrome.tabs.update` 把页面导航到自己的
   `suspended.html`，把原 URL 记下来；用户点击时再导航回去。
   这是曾经被广泛采用的做法。

占位页方案能提供更强的可见性（可以在占位页上做任意 UI），但代价是把页面的
真实状态彻底替换掉：`history`、`sessionStorage`、POST 提交后的页面、
`beforeunload` 语义、站点的 CSP 与 SPA 路由全部被破坏。已有扩展因该方案
衍生的隐私与安全问题被应用商店下架，是这个路线的标志性事故。

## 决策

**只使用原生的 `chrome.tabs.discard()`**，不注入占位页、不改写页面 DOM、
不改变用户看到的 URL。

## 后果

- 正面：
  - 休眠后标签页的标题、图标、URL、位置全部保持不变；
  - 浏览器自己负责重新加载，行为与浏览器内置的"内存节省程序"一致；
  - 没有任何自定义页面参与渲染，攻击面与隐私面都最小化；
  - 不需要 `web_accessible_resources`，也不需要额外的宿主权限。
- 负面 / 需要接受的代价：
  - 页面内 JS 状态（游戏进度、未保存的富文本、复杂 SPA 状态）必然丢失——
    这是 `discard()` 的语义，无法缓解；
  - 只能"尽力"恢复滚动位置与表单值，做不到占位页方案那样的自绘提示；
  - `chrome.tabs.discard()` 拒绝丢弃当前活动的标签页，必须先把用户切走。

## 替代方案

- **占位页替换**：UI 自由度更高，但破坏站点真实行为，且有真实的下架先例。否决。
- **`chrome.tabs.discard()` + 自绘覆盖层**：需要注入 DOM 并常驻修改页面，
  会与站点样式和 CSP 冲突，收益（一个"已休眠"标记）与风险不成比例。否决。
- **不做休眠，只做标签页管理**：放弃了本项目唯一的内存收益来源。否决。
