# 0003. 运行时状态放入 `chrome.storage.session`

- **状态**：已采纳
- **日期**：2026-10-11
- **影响**：启动休眠窗口边界、自动休眠空闲表、所有周期性任务

## 背景

MV3 的 Service Worker 不是常驻进程：**空闲约 30 秒即被浏览器回收**，
下一次事件到达时重新启动。模块级变量在回收后全部丢失。

项目中有两类状态需要跨事件存活：

1. **启动休眠窗口的截止时间**。窗口只有 45 秒，而 Worker 完全可能在窗口中途
   被回收——此时若边界只存在于内存里，重启后的 Worker 会认为窗口不存在，
   清扫静默停止，恢复的标签页就会一起加载。
2. **自动休眠的空闲时间表**（`tabId → 最后活跃时间`）。
   原先它只存在于内存里，Worker 一被回收，所有标签页的计时都从"现在"重新开始。

第 2 条造成的后果很隐蔽：功能开关是打开的，UI 上一切正常，但在实际使用中
标签页几乎永远不会达到空闲阈值——因为每次 Worker 回收都会重置计时。
这类"功能看起来存在但实际不生效"的缺陷不会产生任何报错。

## 决策

**任何需要跨 Service Worker 回收存活的状态，一律放入 `chrome.storage.session`。**

统一入口为 [`src/utils/session-store.js`](../../src/utils/session-store.js)，它对
`chrome.storage.session` 做了封装，并在低版本 Chromium（< 102）上降级为内存 Map。

对照关系：

| 状态                                   | 存储              | 理由                                     |
| -------------------------------------- | ----------------- | ---------------------------------------- |
| 设置、白名单、锁、统计、休眠标签页状态 | `storage.local`   | 需要跨浏览器重启保留                     |
| 启动窗口截止时间、自动休眠空闲表       | `storage.session` | 只在本轮浏览器运行内有意义，退出即应清空 |
| 防抖计时器、批处理进度等瞬时量         | 模块内存          | 丢失无害，甚至应当丢失                   |

## 后果

- 正面：
  - 两个周期性功能在 Worker 回收后可以正确恢复，而不是静默失效；
  - `storage.session` 由浏览器在退出时清空，不需要自己写清理逻辑，
    也不会污染 `storage.local` 的持久数据；
  - 启动休眠在 `initStartupSuspend()` 中统一处理"窗口仍然打开"的恢复路径。
- 负面 / 需要接受的代价：
  - 每次读写是一次异步存储访问，比读内存慢。启动休眠的 `onCreated` 竞态路径
    以毫秒计，因此对设置/白名单/锁额外做了一层内存缓存
    （`startup-suspend.js` 的 `context`，由 `storage.onChanged` 失效）。
  - Chromium 102 以下会退化为内存 Map，此时本类状态在 Worker 回收后仍会丢失。
    `manifest.json` 已声明 `minimum_chrome_version: 102`，降级路径只是兜底。

## 替代方案

- **`chrome.alarms` 携带状态**：alarm 不能携带任意数据，且最小周期 30 秒，
  无法表达 750ms 的清扫节奏。否决。
- **把状态写进 `storage.local`**：能存活但会跨浏览器重启残留——一个 45 秒的窗口
  边界不该活到下次开机；而且需要自己写清理。否决。
- **用 `chrome.runtime.onSuspend` 保存状态**：该事件不保证触发，不可依赖。否决。
- **不依赖状态，每次事件都重新推导**：窗口边界无法推导（唯一信息源就是
  `onStartup` 这一瞬间）；空闲时间本质上就是历史信息。否决。
