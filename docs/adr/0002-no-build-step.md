# 0002. 不引入构建步骤

- **状态**：已采纳
- **日期**：2026-03-17（回溯记录）
- **影响**：整个仓库结构、贡献流程、发布流程

## 背景

Chrome 扩展常见的工程做法是引入打包器（webpack / Vite / rollup）与 TypeScript，
产出 `dist/` 后再加载。可以获得类型检查、代码分割、依赖管理与统一的现代语法。

代价是：贡献者需要理解构建配置；`chrome://extensions` 加载的是产物而不是源码；
调试时源码与运行代码之间存在映射；CI 与本地环境的产物可能不一致；
发布流程多一步且容易忘记执行。

## 决策

**保持零构建**：`src/` 目录就是最终产物，使用原生 ES Module
（`manifest.json` 中 `background.type = "module"`），浏览器直接加载。

## 后果

- 正面：
  - 贡献循环是「改文件 → 点刷新」，30 秒以内；
  - 加载到浏览器的代码与仓库里的代码逐字节一致，调试无需 source map；
  - 打包只是 `zip`，没有任何转译步骤会引入行为差异；
  - 仓库里不存在"产物"与"源码"两种真相。
- 负面 / 需要接受的代价：
  - 没有类型检查。缓解：ESLint 覆盖未使用变量、未定义全局变量；
    `tool/validate.js` 覆盖 manifest 引用、多语言 key、消息协议闭环；
    测试覆盖判定逻辑。
  - 无法 `import` 第三方 npm 包（浏览器不会解析裸模块名）。这被**主动**接受：
    运行时零依赖是本项目的承诺之一。
  - 注入到页面的函数必须自包含（会被序列化后送进页面），所以它们只能共享
    零依赖的纯逻辑。这是 [0008](0008-inject-on-demand-instead-of-content-script.md)
    之后唯一的形态约束。
  - 模块数量增加时会有更多网络请求——在扩展里是本地读取，不构成问题。

## 替代方案

- **TypeScript + Vite**：类型安全收益真实，但会让"克隆下来就能改"变成
  "先装依赖、先构建、再理解配置"。对一个约 2500 行的扩展而言成本高于收益。
- **纯手写打包脚本**：等于自己造一个更差的构建系统。否决。
- **JSDoc + `checkJs`**：不改变运行时形态，是一个可以随时追加的折中选项。
  目前未启用，若要引入类型检查，应优先考虑这一条——见
  [ROADMAP 之后（Later）](../ROADMAP.md)。
